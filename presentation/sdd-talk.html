Spec Driven Development, Harness/Loop Engineering and Everything in Between

Enterprise AI Co-Authoring: From Prompt Engineering to Specs-Driven Development

The Problem: Prompt Engineering Doesn't Scale

Episodic Prompting:

User writes prompt → AI generates code → User inspects and tweaks

Works for snippets. Breaks at enterprise scale.


Confidence vs. Correctness:

LLMs are maximally confident when wrong


Enterprise demands:

  • ✓ Multi-layer validation (compile, test, architecture, coverage, security)
  • ✓ Traceability (which spec? which test? which gate?)
  • ✓ Audit trail (who approved? when? why?)

Meet SDD: Specs-Driven Development

A 7-phase workflow that locks AI into rigid specification → validation loop

1. Specify → gates: no open questions

2. Review Specs → gates: checklist all-green

3. Plan → gates: all ACs traced; no open questions

4. Implement → gates: red→green→refactor logged

5. Test → gates: coverage ≥90% / ≥95% new code

6. Validate → gates: all 10-layer gates green; full traceability

7. Review → gates: zero blockers; human approves

Agent validates its own work. Human reviews the result, not every line.

EARS-lite Specs: Tight Specs = Tight Tests = Honest AI

The Five Shapes

  • Ubiquitous: "The system shall apply a gift card at checkout."
  • Event-driven: "When customer applies a valid gift card, the system shall reduce order total."
  • State-driven: "While order is in PAID state, the system shall reject further redemptions."
  • Optional: "Where multi-currency is enabled, the system shall honor card's home currency."
  • Unwanted: "If gift card code is unknown, the system shall reject with error GC_INVALID."

Open Questions (Q-NNN)

Anything uncertain → mark it Q-001, Q-002, etc. Agent refuses to move forward until you answer.

Example: Gift Card Spec

Acceptance Criteria

  • AC-001: When customer applies valid gift card with balance > 0, the system shall reduce order total by min(balance, total).
  • AC-002: When redemption succeeds, the system shall record redeemed amount in the order receipt.
  • AC-003: If gift card code is unknown, expired, or empty, the system shall reject with error GC_INVALID.

Open Questions

  • Q-001: Should we auto-reverse redemptions on order cancel?
  • Candidate options: (a) auto-reverse, (b) manual refund flow, (c) reject cancellation
  • Status: open

TDD by Construction: Red → Green → Refactor → Simplify

Phase 4 is Strict TDD

  • Red: Test-engineer writes smallest failing test(s)
  • Green: Implementer writes minimum code to pass
  • Refactor: Clean up with tests still green
  • Simplify: Apply clarity-over-cleverness

Enforcement

A hook prevents production code edits unless .tdd-state.json shows a failing test for the active task.

→ LLM that can only write code after a test fails will never invent features.

The 10-Layer Harness: Self-Validation

# Layer Tool Failure means
1 Format & Lint Spotless, Checkstyle Style drift
2 Compile javac Code doesn't build
3 Static analysis SpotBugs, Error Prone Bug-prone patterns
4 Architecture ArchUnit Boundary violation
5 Unit + slice tests JUnit 5, Surefire Logic regression
6 Integration tests Failsafe, Testcontainers DB / broker regression
7 Coverage JaCoCo <90% overall / <95% new
8 Mutation PIT Surviving mutants
9 Contract OpenAPI + diff Breaking API change
10 Security OWASP Dep Check Known CVE in tree

Why a Harness, Not Vibes?

  • Deterministic: Same commit → same gate outcome. No time-based flake.
  • Fail-fast: Cheap gates run first. Agent gets actionable feedback immediately.
  • Parseable: Every layer emits machine-readable reports (XML, JSON). Agent reads and adjusts.
  • Baseline-aware: Brownfield repos track pre-existing failures. Only regressions block.
  • Incremental: Coverage and mutation run incrementally locally (full in CI nightly).

Same `.github/scripts/harness.sh` runs locally and in CI. No second source of truth.

Loop Engineering: A Control System, Not "Run It Again"

A loop observes the world, compares it to a goal, acts to close the gap, then observes again. The skill isn't in the acting — agents are already good at that. It's in defining what it observes and when it's allowed to stop.

The Shape

observe → goal met? → yes: stop, merge-ready
                     → no: act (fix + push)
budget left? → yes: wait → observe again
            → no: stop, escalate to human

Escalating isn't failure — it's the loop doing its job.

Anatomy of an Agentic Loop: Six Parts

  • Goal: a checkable definition of "done" — not "make it good"
  • Sensors: how it observes state (CI status, coverage report, Sonar API, test re-runs)
  • Action: what it changes to close the gap (fix, write a test, commit, push)
  • Cadence: how often it runs — event-driven vs. as-fast-as-the-work-allows
  • Bounded budget: max iterations or wall-clock cap — the escape hatch
  • Guardrails: what it must never do (merge, force-push, disable a test)

Name all six and you have a loop. Otherwise, you have a prompt you're running by hand.

Loop 1: The Ship Loop — a PR That Drives Itself Green

The Loop Engine

while harness not all-green:
  1. Run harness.sh
  2. Parse reports (Surefire XML, JaCoCo XML, PIT XML, etc.)
  3. Synthesize exact code modifications needed
  4. Commit minimal changes
  5. Re-run harness
  repeat (stop at budget; post result and escalate)

Real Example Timing

  • Iteration 1: Coverage fails at 87% → add edge-case test
  • Iteration 2: Mutation survivors appear → tighten boundary logic
  • Iteration 3: All 10 layers ✓ → task complete
  • Total agent time: 5–10 min (vs. 70 min human manual work)

Inside the Ship Loop: Four Gate Shapes

Gate Loop shape "Done" means Failure mode
Tests + Checkstyle + Sonar Converge-to-green Every check passes Oscillating: fixing A breaks B
Coverage Incremental-to-a-number Metric crosses threshold Gaming the metric (empty tests)
Dependency upgrade Queue / batch Work queue is empty Getting stuck on one hard item
Flaky-test stabilizer Repeat-until-confident Confidence over N runs Declaring victory after one run

Same outer loop. Each gate just answers "are you green?" in its own way.

Loop 2: The Build Loop — Spec to a Clean, Reviewed Branch

Goal / Sensors / Action

Drains the .tdd-state.json task queue (T-001, T-002, …) via /build, then converges on /validate + /review until APPROVE with zero must-fix findings.

Cadence & Budget

Self-paced — no CI to wait on, so it runs the next step the instant the last one finishes. Capped at 5 review-fix rounds before escalating.

Guardrails

Feature branch only, never main. Never merges or opens the PR. Never weakens a test, lowers a threshold, or edits the spec to force a pass.

The Full Pipeline: Four Loops, Two Human Checkpoints

Loop Cadence Converges on
Spec-sharpening Human-paced /spec-review PASS, zero open questions
Build loop Self-paced Tasks done, /validate clean, /review APPROVE
Ship loop Polls CI (~10 min) All gates green, merge-ready
Review-response Polls review activity No unresolved threads, gates stay green

Human judgment lands at exactly two points: is the intent right, and is this branch worth a PR?

Trust Gate: Earning the Right to Auto-Commit

You're ready when...

  • /review rarely surfaces something you disagree with
  • Your skills encode your team's standards, not generic defaults
  • Your sensors actually fail loudly on the mistakes you care about
  • The spec passed /spec-review with zero open questions
  • The feature is a pattern you've shipped before

Non-negotiables, always

  • Feature branch only, never main
  • Mandatory human validation round before the PR opens
  • Bounded budget on every review-fix round

Trusting AI 100% is a disaster waiting to happen — it's still your name on the commit.

Pre-Commit Code Review: Agent + Human

Phase 7: Code Review Rubric

  • ✓ Spec alignment (every change maps to an AC?)
  • ✓ Design contract (boundaries respected? ArchUnit passed?)
  • ✓ Spring idioms (constructor injection? Records? No Lombok?)
  • ✓ Test quality (Arrange/Act/Assert? Name behavior?)
  • ✓ Security baseline (no auth bypass? No SQL injection?)
  • ✓ Mutation score (did we add code that survives mutations?)
  • ✓ Clarity (readable? Can a junior engineer understand it?)

Severity Classification

Blocker | Major | Minor | Nit

Verdict: Zero blockers/majors → APPROVED. Human still approves the PR.

End-to-End: Spec → Ship in 6 Minutes

Phase 1: Spec

Draft `01-spec.md` → User answers Q-NNN → Phase complete

Phase 2: Spec Review

Run checklist: testable? atomic? no implementation leakage? → Produce `02-spec-review.md`

Phase 3: Plan

Produce `03-design.md` (architecture, API shapes, DB schema) + `04-tasks.md` (T-001, T-002, ...)

Phase 4: Implement

For each task: red test → green code → refactor → simplify → coverage ≥95%

Phase 6: Validate

Run harness → all 10 layers ✓ → produce `07-validation-report.md` + `07a-traceability.md`

Phase 7: Review

Produce `08-code-review.md` → APPROVED

Commit

You run `git commit` (agent never commits automatically)

SDD vs. Prompt Engineering

Aspect Prompt Engineering SDD
Spec "build me a checkout flow" Atomic ACs + open questions + review
Test "seems good" Red→green→refactor logged + TDD enforced
Validation Run tests manually 10-layer harness, all automated, reports parseable
Traceability None AC ↔ test ↔ code ↔ gate
Regression Who knows? Baseline + diff catch new failures
Audit "I wrote this" Full artifact chain + phase gates
Re-run Manual; different every time Deterministic; same code → same result
Human role Inspect every line Review result + approve code review

Production-Ready AI Means Defensive, Not Daring

The Enterprise Reality

You need code that compiles, passes tests, maintains architecture, covers edge cases, avoids CVEs, and stays auditable.

SDD is the Guardrail Framework

  • Tight specs lock in scope upfront
  • TDD lock-in prevents invention
  • 10-layer harness catches any slip
  • Traceability chain proves what shipped and why
  • Agent loops until the build is green

The Result

  • Features ship faster (no back-and-forth)
  • They're more reliable (caught by gates, not manual testing)
  • They're auditable (full artifact trail)
  • Your team stays in control. The agent is a co-author, not a black box.
